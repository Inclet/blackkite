# Phase 4 contracts

Fixed before Phase 4 work starts so three tracks can build in parallel. Change only through the orchestrator.

## 1. Scoring output (scoring track writes, member API reads)

One `user_opportunity_score` row per (user, opportunity, profile). Columns: `score` (0–100, internal, never shown), `score_reason` (one sentence), `score_breakdown` (jsonb):

```json
{
  "version": 1,
  "components": {"fit": 0-40, "eligibility": 0-20, "value": 0-15, "time": 0-15, "source": 0-10},
  "fit_confidence": 0.0-1.0,
  "eligibility_confidence": 0.0-1.0,
  "fit_word": "strong" | "good" | "possible" | null,
  "reasons": ["It asks for transport, warehousing and logistics support, which you offer."],
  "flags": [{"code": "owned_fleet", "label": "May require owned fleet", "quote": "copies of vehicle logbooks", "to_check": "WFP's transport call asks for vehicle logbooks, so this one may require an owned fleet."}],
  "provisional": false,
  "hard_filtered": null | "outside_rwanda" | "deadline_passed" | "stream_not_selected" | "muted_source_only" | "ineligible" | "below_min_value",
  "model": "claude-haiku-5-5", "prompt_version": "score-v1", "scored_at": "ISO-8601"
}
```

- `fit_word` rule (revised 2026-11-25 to match the boards; owner to confirm): **strong** when fit_confidence ≥ 0.7 and eligibility_confidence ≥ 0.7 (flags allowed: the WFP item is Strong with a "To check" note); **good** when fit_confidence ≥ 0.6 and eligibility_confidence ≥ 0.5 ("matches, with something to check"); **possible** when fit_confidence ≥ 0.4 (eligibility unclear); otherwise null (not shown). Thresholds in config. Investments and events: fit_word null (decision 24 / boards), ranked on time, verification and source kind (spec 7.1).
- Hard-filtered pairs are stored with `hard_filtered` set and never shown or sent.
- A user's best profile for an item = highest score among non-filtered rows; that profile's name is the item's `profile`.

## 3. Digest (member-API track)

`DigestView` from `api/blackkite/delivery/digest.py` is built from scores: top items across the user's profiles, capped at 12, each stream capped (investments and events at 3 each, spec 7.1), plus a "closing in 7 days" block for saved items and the value line (spec 8). Weekly on Monday; urgent alert for items above the user's threshold closing within 5 days, the day they are found. Delivery is Mailpit/console only; nothing real is sent without the owner's go-ahead.

### 4.2 Renderer service (decision 46, added 2026-11-26)

Not web-facing: the web app never calls it. Headless Chromium for `browser_list` (scheduled runs and admin test runs) runs in its own container, `renderer` (`bk renderer`, `api/Dockerfile` target `renderer`), instead of in the API or worker, whose image (target `app`) no longer contains a browser. Test runs keep the same `PreviewOut` shape; a browser_list failure reads as before ("robots.txt disallows ...", "... did not load in 45 s", "blocked: ... is not a public address"), plus the renderer's own messages ("the renderer is busy; try again later", "cannot reach the renderer at ...", "browser_list needs the renderer service: set BK_RENDERER_URL and BK_RENDERER_TOKEN ...").

Isolation:
- No secrets. The renderer reads no `.env` file and refuses to start (exit 2) if any of `BK_DATABASE_URL`, `ANTHROPIC_API_KEY`, `VOYAGE_API_KEY`, `BRAVE_API_KEY`, `RESEND_API_KEY`, `BK_UNSUBSCRIBE_SECRET`, `BK_CALENDAR_SECRET`, `BK_INGEST_IMAP_PASSWORD`, `BK_SMTP_PASSWORD` or `POSTGRES_PASSWORD` is present in its environment, even empty. Compose gives it no `env_file`, no volumes, non-root user, all capabilities dropped.
- Networks: `render-internal` (internal, no route out) joins only api, worker and renderer; `render-egress` is the renderer's own way out. The renderer is not on the default network, so it cannot see the database; its URL guard refuses non-public addresses anyway.
- The renderer does not trust its caller: it applies the URL guard (and the guarded transport for every request the page makes), robots.txt on every main-frame navigation including redirects and script navigations (decision 48), per-host pacing across all callers (at least `BK_RENDERER_MIN_HOST_DELAY`, raised by robots Crawl-delay), its own limit ceilings, and the per-render timeout with the browser's process group killed on overrun. The API and worker still check robots.txt and pace the top-level page on their side as well.

HTTP:

| Route | Auth | Body | Returns |
|---|---|---|---|
| `GET /healthz` | none | | `{"ok": true}` |
| `POST /render` | `Authorization: Bearer <BK_RENDERER_TOKEN>`; 401 without it or with a wrong one | `{url, wait_for?, limits?: {timeout_seconds, max_bytes, total_bytes, max_requests, subresource_delay, request_timeout}}` (snake_case, unknown keys 422; each limit optional and clamped to the renderer's ceiling: never more time, bytes or requests, never less delay) | 200 `{ok: true, url (final), html, requests, blocked: [url], request_log: [{url, method, type, outcome, status?}], limits (effective)}` or 200 `{ok: false, kind: unsafe_url\|robots\|rate_limited\|render, error, request_log, limits}`; 503 when every browser stays busy for `BK_RENDERER_QUEUE_WAIT_SECONDS`; 422 for a malformed body. `outcome`: fulfilled, redirected, blocked (URL guard), robots, refused (resource type, method or download), limit, failed. |

No OpenAPI or docs pages are served.
