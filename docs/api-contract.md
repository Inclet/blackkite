# Phase 4 contracts

Fixed before Phase 4 work starts so three tracks can build in parallel. Change only through the orchestrator.

## 1. Scoring output (scoring track writes, member API reads)

One `user_opportunity_score` row per (user, opportunity, profile). Columns: `score` (0–100, internal, never shown), `score_reason` (one sentence), `score_breakdown` (jsonb):

```json
{
  "version": 1,
  "components": {"fit": 0-40, "eligibility": 0-20, "value": 0-15, "time": 0-15, "source": 0-10},
  "fit_confidence": 0.0-1.0,
  "eligibility_confidence": 0.0-1.0,
  "fit_word": "strong" | "good" | "possible" | null,
  "reasons": ["It asks for transport, warehousing and logistics support, which you offer."],
  "flags": [{"code": "owned_fleet", "label": "May require owned fleet", "quote": "copies of vehicle logbooks", "to_check": "WFP's transport call asks for vehicle logbooks, so this one may require an owned fleet."}],
  "provisional": false,
  "hard_filtered": null | "outside_rwanda" | "deadline_passed" | "stream_not_selected" | "muted_source_only" | "ineligible" | "below_min_value",
  "model": "claude-haiku-5-5", "prompt_version": "score-v1", "scored_at": "ISO-8601"
}
```

- `fit_word` rule (revised 2026-11-25 to match the boards; owner to confirm): **strong** when fit_confidence ≥ 0.7 and eligibility_confidence ≥ 0.7 (flags allowed: the WFP item is Strong with a "To check" note); **good** when fit_confidence ≥ 0.6 and eligibility_confidence ≥ 0.5 ("matches, with something to check"); **possible** when fit_confidence ≥ 0.4 (eligibility unclear); otherwise null (not shown). Thresholds in config. Investments and events: fit_word null (decision 24 / boards), ranked on time, verification and source kind (spec 7.1).
- Hard-filtered pairs are stored with `hard_filtered` set and never shown or sent.
- A user's best profile for an item = highest score among non-filtered rows; that profile's name is the item's `profile`.

## 3. Digest (member-API track)

`DigestView` from `api/blackkite/delivery/digest.py` is built from scores: top items across the user's profiles, capped at 12, each stream capped (investments and events at 3 each, spec 7.1), plus a "closing in 7 days" block for saved items and the value line (spec 8). Weekly on Monday; urgent alert for items above the user's threshold closing within 5 days, the day they are found. Delivery is Mailpit/console only; nothing real is sent without the owner's go-ahead.

### 4.2 Renderer service (decision 46, added 2026-11-26)

Not web-facing: the web app never calls it. Headless Chromium for `browser_list` (scheduled runs and admin test runs) runs in its own container, `renderer` (`bk renderer`, `api/Dockerfile` target `renderer`), instead of in the API or worker, whose image (target `app`) no longer contains a browser. Test runs keep the same `PreviewOut` shape; a browser_list failure reads as before ("robots.txt disallows ...", "... did not load in 45 s", "blocked: ... is not a public address"), plus the renderer's own messages ("the renderer is busy; try again later", "cannot reach the renderer at ...", "browser_list needs the renderer service: set BK_RENDERER_URL and BK_RENDERER_TOKEN ...").

Isolation:
- No secrets. The renderer reads no `.env` file and refuses to start (exit 2) if any of `BK_DATABASE_URL`, `ANTHROPIC_API_KEY`, `VOYAGE_API_KEY`, `BRAVE_API_KEY`, `RESEND_API_KEY`, `BK_UNSUBSCRIBE_SECRET`, `BK_CALENDAR_SECRET`, `BK_INGEST_IMAP_PASSWORD`, `BK_SMTP_PASSWORD` or `POSTGRES_PASSWORD` is present in its environment, even empty. Compose gives it no `env_file`, no volumes, non-root user, all capabilities dropped.
- Networks: `render-internal` (internal, no route out) joins only api, worker and renderer; `render-egress` is the renderer's own way out. The renderer is not on the default network, so it cannot see the database; its URL guard refuses non-public addresses anyway.
- The renderer does not trust its caller: it applies the URL guard (and the guarded transport for every request the page makes), robots.txt on every main-frame navigation including redirects and script navigations (decision 48), per-host pacing across all callers (at least `BK_RENDERER_MIN_HOST_DELAY`, raised by robots Crawl-delay), its own limit ceilings, and the per-render timeout with the browser's process group killed on overrun. The API and worker still check robots.txt and pace the top-level page on their side as well.

HTTP:

| Route | Auth | Body | Returns |
|---|---|---|---|
| `GET /healthz` | none | | `{"ok": true}` |
| `POST /render` | `Authorization: Bearer <BK_RENDERER_TOKEN>`; 401 without it or with a wrong one | `{url, wait_for?, limits?: {timeout_seconds, max_bytes, total_bytes, max_requests, subresource_delay, request_timeout}}` (snake_case, unknown keys 422; each limit optional and clamped to the renderer's ceiling: never more time, bytes or requests, never less delay) | 200 `{ok: true, url (final), html, requests, blocked: [url], request_log: [{url, method, type, outcome, status?}], limits (effective)}` or 200 `{ok: false, kind: unsafe_url\|robots\|rate_limited\|render, error, request_log, limits}`; 503 when every browser stays busy for `BK_RENDERER_QUEUE_WAIT_SECONDS`; 422 for a malformed body. `outcome`: fulfilled, redirected, blocked (URL guard), robots, refused (resource type, method or download), limit, failed. |

No OpenAPI or docs pages are served.

**Own private items (orchestrator decision 2026-11-26):** the caller's own private items always appear in their feed, shortlist and calendar, bypassing hard filters as well as decision 41 (stream not selected, outside Rwanda, below minimum value, ineligible, …); such an item's `fit` is null. With `profile=`, an own item stays when that profile scored it at all, filtered or not. Expired own items behave like tracked items: not in the default (open) feed, shown under closed `status` filters and on the calendar. Digest and urgent-alert eligibility is unchanged (still needs a fit word). Other users never see them. **Extended 2026-11-26:** an item the caller added that an admin since published (`madePublicAt` set, caller still the owner) counts as the caller's own for all of the above, including the "muted source only" filter, and `GET /api/opportunities/{id}` always returns it to the owner; other users see it by the normal public rules (fit rule, hard filters, mutes).

`GET /api/opportunities/{id}` already returns `detail.fields`, `sources`, `documents` (names only), `changes`, `note`; the web now shows them (spec 8 "Opportunity page"). **built:** `detail.ownItem {shareConsent, published}` is sent only on the caller's own manual item (private or published), left out otherwise. **built:** `detail.isManual` (always sent): true for items a member added, private or since published (no source carries them; `originalUrl` is the link the member gave). **Built 2026-11-26:** also on every `FeedItem.detail` (feed, shortlist), same meaning, always sent. `detail.fields[]` gains `display?` for `valueAmount`: the digest's wording ("FRW 6,000,000", currency code as stored, RWF shown as FRW); `value` is unchanged (the decimal as a string, e.g. "6000000.00"). Left out for other fields.

`GET /api/feed` filters per spec 8, all combinable: `stream`, `profile`, `window` (days), `verification`, `source`, `state`, plus **built:** `status=open|closing_soon|expired|awarded|cancelled` (repeatable; the item's current status from its dates) — closed statuses list only items the caller tracks (saved/acting/done) or owns, since untracked closed items are hard-filtered; and `fit=strong|good|possible`, at least that word (strong ⊂ good ⊂ possible). **Revised 2026-11-26:** `fit` narrows tenders and funding only; there, items without a word (not scored, below "possible", closed) are left out, and so is the caller's own private tender or funding item with no word (decision 50 otherwise unchanged). Events and investments never carry a word (decision 24) and pass through a fit filter unaffected; they are still subject to the other filters. Never a number.

Export and deletion (spec 10): `GET /api/me/export` adds `privateItems[].url`, `.shareConsent`, `.shareConsentAt`, `.madePublicAt`, `publishedItems` (the caller's items an admin made public, same shape) and `calendarFeed {rotatedAt}` (the link itself is not exported). `DELETE /api/me` removes private items; published ones stay public with the owner link cleared.

Logs: **built:** `token=` query values (calendar feed, unsubscribe GET/POST) are rewritten to `token=[redacted]` in uvicorn's access log and the app's logs (`blackkite/logredact.py`); the reverse proxy must redact its own access log the same way (`.env.example`).

### 6.1 As built (2026-11-26)

**Amounts.** Every amount (`median`, `p25`, `p75`, `min`, `max`, `winningPrice`, bidder `price`, `estimatedValue`, preview amounts) is a decimal **string** with two places ("6250000.00"), in the entry's `currency` (three letters as stored; RWF shown as FRW by the web), as `detail.fields[].value` already is. `medianBidders` is a number (may be x.5).

**Schema (migration 0018).** `award` gains `ref_key`/`entity_key` (dedupe keys, unique together: the normalised tender ref, or `title:<normalised title>` without a ref; the normalised entity, "" when unknown), `title`, `amount` + `currency` (the winning price), `awarded_on`, `category` (primary, default `other`) + `tags`, `url`, `opportunity_id`, `raw` (`{listed: {field: text as listed}, problems: [...]}`, the supporting text of every stored amount and date), `first_seen`/`last_seen`/`updated_at`; `bidders` stays `[{name}]`, `prices` `[{bidder, amount, currency}]`. Indexes: (category, currency), entity_key, awarded_on, tags (GIN), opportunity_id. New `procurement_plan_item`: entity(+key), description(+key), category + tags, method, estimated_amount + currency, fiscal_year ("2026/27"), planned_quarter (Q1–Q4, as the plan wrote it), planned_date, planned_start/planned_end (the period as dates, both or neither), tender_ref, url, embedding, opportunity_id, source_id, raw, timestamps; unique (entity_key, description_key, fiscal_year) NULLS NOT DISTINCT; indexes on category, entity_key, (planned_start, planned_end), tags.

**Categories** (`pipeline/categories.py`, rules only, no model): `consultancy`, `transport`, `construction`, `ict`, `office`, `food`, `cleaning_security`, `medical`, `agriculture`, `energy`, `vehicles`, else `other`, each with a plain label ("Transport and logistics"). Keywords in the title (awards) or description (plans); primary = most keyword hits, ties by that order. Tags are `sector:<key>`, the extraction tag vocabulary. A catalogue tender's category is a `sector:<key>` tag naming a category, else its title/subtype/summary/tag keywords.

**Collectors.** `custom` with `collector: "umucyo_awards"` or `"umucyo_plans"` (`collectors/umucyo.py`). Options: `list_url`, `pagination_pattern` ({page}), `first_page`, `max_pages` (≤ 50), `max_items` (≤ 2000), `date_formats` (strftime, each must contain a year; empty = day-first dates with a written year), `amounts {decimal_separator, thousands_separators, currency?}` (`currency` = the page's currency for amounts that name none; empty = kept without currency and left out of statistics), `selectors` (a CSS string or `{css, attr}` per field). Awards: `item` (required), `tender_ref`/`title` (at least one), `entity`, `winner`, `amount`, `currency`, `award_date`, `period`, `link`, `bidders {row, name, price?}`, optional `detail {selectors, max_items}` (values on the award's own page replace the list's). Plans: `item`, `description` (required), `entity`, `method`, `estimated_value`, `currency`, `planned_date`, `planned_quarter`, `fiscal_year`, `tender_ref`, `link`; `page {entity?, fiscal_year?}` read once from the page; `quarter_basis` `fiscal` (Q1 = July–September) or `calendar`, required with `planned_quarter`. They fetch through the guarded client (URL guard, robots.txt, rate limit, size caps), return no `RawItem`, and expose `records` (the new optional collector hook, `collectors/base.Records`). Rows with no field are skipped silently; rows missing the required fields become run warnings `{kind: "record_skipped", message}`. `GET /api/admin/collector-types`: the `custom` entry gains `collectors: [{name, help, fields}]` (each allowlisted collector with its option fields, same field format; left out on other types).

**Ingest** (`pipeline/awards.py`, `pipeline/plans.py`, `pipeline/records.py`; never `opportunity`). Normalise: entity labels ("Procuring entity:") dropped; amounts must be one number in the configured separators, with the currency from the text, a currency cell, or the config (a disagreement, a range or several numbers leaves the amount out); dates only with an explicit year (awards: not in the future, ≤ 10 years back; plans: 2 years back to 3 ahead); a quarter becomes dates only with the stated basis and a fiscal year (or a calendar year written in the cell); never guessed, the reason is kept in `raw.problems`. Dedupe as the keys above; a re-listing updates the row (empty new values keep old ones). Plan descriptions are embedded when `VOYAGE_API_KEY` is set. Link to a **public** tender: the record's tender ref (≥ 5 characters with a digit) in the tender's title or evidence text, else entity similarity ≥ 85 (acronyms count) and title similarity ≥ 90 (awards token_sort, plans token_set), generic titles never; a plan only to a tender first seen no earlier than 180 days before its planned period or fiscal year. The opportunity ingest offers every tender it creates or updates to `link_tender` (records seen in the last 400 days). Runs count records in `items_found`/`items_new`/`items_failed`, so the promotion gate works as for other sources. **Test run:** `PreviewOut.records` (always sent, `[]` for other collectors): `{kind: "award", url, tenderRef, title, entity, winner, amount, currency, awardedOn, period, bidders: [{name, price}], category, categoryLabel, problems}` or `{kind: "plan", url, entity, description, method, estimatedValue, currency, fiscalYear, plannedQuarter, plannedStart, plannedEnd, plannedLabel, category, categoryLabel, problems}`; `totalParsed` counts them; nothing is written.

**Visibility.** Awards and plans are shown only from `active` or `paused` sources (as opportunities, spec 4.3 and decision 25), to members and admins alike.
